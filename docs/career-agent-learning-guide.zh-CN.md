# Career Agent 工程学习指南

> 面向通过本项目学习 Agent 工程的开发者。本文不是框架速查表，也不把未来设想写成已经实现的功能；它把核心概念、当前代码、练习、测试方法和后续阶段连接起来。

## 1. 先回答三个关键问题

### 1.1 这些知识是否应该记录

应该，但不应只记录“什么是 Prompt、RAG、Memory”之类容易过时的术语。更有价值的是同时记录四类内容：

1. **概念**：这个机制解决什么问题，与相近概念有什么区别；
2. **项目映射**：它在当前代码中的位置，哪些部分已实现、哪些只是计划；
3. **决策证据**：为什么选择这种设计，比较过哪些方案，什么证据可能推翻它；
4. **验证结果**：如何测试、失败过什么、还剩下哪些不确定性。

项目文档因此既是开发资料，也是学习档案。以后回看时，重点不是“当时用了哪个框架”，而是能否解释问题、边界、权衡和验证方法。

### 1.2 当前实现算不算 Agent

要看采用哪一层含义：

- 从类名和产品能力看，`ResumeTailoringAgent` 是一个使用 LLM、分阶段处理输入并产出结果的 Agent 能力；
- 从严格的编排方式看，它目前更接近**有界的 LLM 工作流**：执行阶段由代码预先确定，模型还不能根据目标动态选择能力和工具；
- 从完整产品看，它只是未来 Career Agent 的第一个能力模块，还不是能够理解长期目标、暂停恢复、调用多种工具和持续陪伴用户成长的顶层 Agent。

这三个描述并不冲突。类名是否含有 `Agent` 不是判定标准，关键在于谁决定下一步、可使用哪些工具、状态如何保存、失败如何恢复，以及系统如何被评测。

### 1.3 是否必须先使用 Agent 框架或脚手架

不必须。框架可以提供 Agent 循环、工具调用、持久化、Human-in-the-loop、Trace 和 handoff，但不会替代本项目自己的：

- 职业档案和证据模型；
- 能力边界与权限策略；
- 事实保真规则；
- 交互协议；
- Eval 数据集和验收标准。

当前阶段先手工理解一次完整的调用、校验、Repair、状态转换和恢复机制，更有利于建立基础。等项目真正需要异步运行、暂停恢复和多能力路由时，再用同一组验收场景比较自建状态机、LangGraph、OpenAI Agents SDK 等候选方案。选择标准应是可恢复性、可测试性、权限控制、可观测性和迁移成本，而不是示例代码最短。

## 2. 核心词汇及其边界

| 概念 | 在本项目中的含义 | 常见误解 |
| --- | --- | --- |
| LLM 应用 | 任何把模型调用嵌入产品的软件 | 有模型就一定是 Agent |
| 工作流（workflow） | 步骤和分支主要由代码预先规定 | 工作流比 Agent “低级” |
| Agent | 模型在明确边界内根据当前目标和状态决定下一步、选择工具或请求输入 | 必须无限循环或完全自主 |
| Runtime / Orchestrator | 管理运行、状态、路由、工具、权限、预算、重试和事件的执行层 | 它就是某个模型 SDK |
| Capability | 能独立描述输入、输出、权限和验收标准的领域能力，例如简历定制 | 每个 Capability 都必须是一个独立 Agent |
| Tool | Agent 可调用的窄接口，例如搜索、读文件、渲染或查询岗位 | 把一整套业务流程包装成一个模糊工具 |
| Run | 一次有身份、有状态、可追踪的任务执行 | 等同于一次 HTTP 请求 |
| Session | 一段连续交互及其上下文边界，可包含多个 Run | 等同于把全部聊天记录塞给模型 |
| State | 运行当前阶段所需的结构化事实和中间结果 | 只有聊天消息才是状态 |
| Checkpoint | 可用于恢复、重放或审计的持久化状态快照 | 只在内存里保存一个对象 |
| Memory | 经同意保存并能在未来任务中正确取用的信息 | 无限制永久保存所有对话 |
| Human-in-the-loop（HITL） | 系统因缺失事实、冲突、选择或风险而暂停，等待人类输入后恢复 | 结果生成完再让用户点确认 |
| Guardrail | 约束输入、输出、事实、预算或行为的规则 | 再写一句“不要编造”的 Prompt |
| Approval | 对有副作用或高风险动作的显式授权 | 所有步骤都让用户确认一遍 |
| Structured Output | 模型输出先经过 Schema 和领域约束验证，才能进入后续阶段 | JSON 能解析就代表数据正确 |
| Retrieval / RAG | 按当前任务检索外部或内部证据，再让模型基于证据工作 | 向量数据库本身就是知识库质量 |
| Citation | 让结论能够追溯到具体来源、时间和片段 | 在答案末尾放几个链接即可 |
| Eval | 用代表性数据和明确标准测量非确定性行为 | 单元测试通过就证明模型效果好 |
| Observability | 记录阶段、耗时、token、错误类别和安全元数据以诊断运行 | 记录用户简历全文和原始 completion |

最重要的区分是：**模型负责需要语义判断的部分，确定性代码负责契约、权限、事实、状态转换和副作用。** 两者需要协作，不应让其中一方包办全部工作。

## 3. 把概念映射到当前代码

### 3.1 已实现的学习样本

| 主题 | 当前代码 | 可以学到什么 |
| --- | --- | --- |
| 有界编排 | `packages/resume-agent/src/workflow/agent.ts` | 输入提取、归一化、JD 分析、匹配、草拟、验证、评估和渲染的固定执行链 |
| 数据契约 | `packages/resume-agent/src/contracts.ts` | 用 Zod 和 TypeScript 定义 LLM 边界、API 输入和领域结果 |
| 结构化输出 | `packages/resume-agent/src/llm/structured-output.ts` | Schema 验证、有限兼容归一化、最多有限次数的 Repair 和安全错误摘要 |
| 模型适配器 | `packages/resume-agent/src/llm/openai-compatible.ts` | 将供应商调用、超时、传输重试和 token 元数据隔离在 `LlmClient` 后面 |
| Prompt 边界 | `packages/resume-agent/src/prompts.ts` | JD 分析与草拟是不同任务，应有不同输入、策略和输出契约 |
| 证据模型 | `packages/resume-agent/src/validation/evidence.ts` | 把候选人事实变成稳定 evidence ID，供后续结果引用 |
| 确定性匹配 | `packages/resume-agent/src/matching/match.ts` | 不是所有判断都必须交给 LLM；当前词法匹配也明确保留了待评测缺口 |
| 事实和 Schema 防线 | `packages/resume-agent/src/validation/resume.ts` | 模型草稿必须通过简历 Schema、不可变事实和领域规则 |
| 透明结果 | `packages/resume-agent/src/transparency/` | 用 Diff 和 QualityReport 告诉用户改了什么、覆盖了什么、缺了什么 |
| 产物边界 | `packages/resume-agent/src/rendering/` | 让确定性渲染器生成多种格式，而不是让模型直接写 PDF 或 HTML |
| 可替换测试 | 相邻的 `*.test.ts` | 用 fake LLM 稳定复现成功、畸形输出、Repair 和拒绝路径 |

当前工作流的主要数据流可以简化为：

```text
用户资料 + JD
      │
      ▼
文件提取与候选人归一化 ── LLM + Schema
      │
      ├──→ 证据索引 ──────────────┐
      │                           │
      ▼                           │
JD 结构化分析 ───────── LLM + Schema
      │                           │
      ▼                           │
确定性需求匹配 ◀─────────────────┘
      │
      ▼
证据约束草拟 ────────── LLM + Schema
      │
      ▼
事实校验 → Diff / Quality → 确定性渲染
```

### 3.2 已有接口不等于完整能力

当前代码已经把 `FollowUpQuestion` 扩展为可选的判别联合控件，并在异步 Run
中实现 `needs_input → answer → resume` 的开发级闭环：服务端一次公开一个重点
问题，验证回答，写回候选人 checkpoint，再从 JD 分析继续。内部可信 record 与
公开 Run 快照已经分离，幂等记录只保存回答指纹。

这证明了主动交互的最小机制，但还不能宣称达到 Codex 或 Claude Code 的生产
可靠性。当前已经有结构化控件、状态转换和回答命令，完整能力仍至少需要：

- `single_choice`、`multi_choice`、`text`、`textarea`、`number`、`date`、`file` 和 `confirm` 等结构化控件；
- 选项、推荐理由、自定义输入、校验规则、隐私提示和稳定字段 ID；
- durable `Run / Session / Checkpoint` 持久化模型和版本迁移；
- 并发回答的 compare-and-set / version lock；
- 进程重启、多实例、取消、过期和恢复测试；
- 前端根据同一协议渲染输入框或选择器，而不是解析自然语言。

已实现部分是 `Implemented for development / Partial`；durable recovery 与生产
安全仍是明确缺口。`date` 控件当前只接受 `YYYY-MM-DD`，`file` 控件只验证
既有文件引用，这两个限制也适合用来学习“协议存在”和“完整能力可用”的区别。

## 4. 与本项目一致的学习路线

每一阶段都应产生代码、测试和一份可解释的学习记录。不要同时学习所有框架和所有概念。

### 阶段 A：读懂并打磨有界简历工作流

目标：能解释每一次 LLM 调用为什么存在、输入输出是什么、哪一部分由确定性代码保护。

重点：

- TypeScript 接口和 Zod Schema；
- Prompt 与业务规则的边界；
- 结构化输出、解析失败、领域校验失败和 Repair；
- evidence ID、不可变事实和幻觉防护；
- fake LLM 单元测试与真实模型 Eval 的区别；
- 文件解析、渲染失败、隐私和安全日志。

完成证据：能够从一次请求一路追踪到最终产物；能主动构造畸形模型输出并说明系统在哪一层拒绝它；当前 P0 退出门槛有可复现结果。

### 阶段 B：实现 Run、Checkpoint 和 Human-in-the-loop

目标：任务能够暂停、保存、接收结构化回答，并从正确阶段恢复。

重点：

- 显式状态机和合法状态转换；
- checkpoint 版本、幂等键和并发更新；
- 哪些中间结果可复用，哪些必须重算；
- 问题和输入控件协议；
- 取消、超时、过期、重试和数据保留。

完成证据：进程重启后仍能恢复；重复提交答案不会产生重复副作用；回答只会使受影响的阶段重新执行。

### 阶段 C：建立顶层 Career Agent Runtime

目标：顶层入口可以理解用户意图、选择一个或多个 Capability，并维护跨任务职业上下文。

重点：

- `Capability Registry` 的窄接口；
- 意图路由、计划和重新规划；
- 领域状态与框架对象解耦；
- 运行预算、权限和统一事件协议；
- 单能力失败时的降级和恢复。

完成证据：同一 Runtime 至少能路由两个小型能力；能力可以被单独测试；模型适配器或编排实现可以替换而不迁移职业档案模型。

### 阶段 D：增加有权限边界的工具调用

目标：Agent 能根据需要选择工具，但工具不能越权或无限运行。

重点：

- 名称清晰、输入窄、结果结构化的工具 Schema；
- allowlist、作用域、超时、最大调用次数和预算；
- 只读工具与有副作用工具的区别；
- 高风险调用前审批；
- 工具错误、部分成功、重复调用和幂等性。

先添加一个低风险、只读工具完成闭环，再考虑浏览器、MCP 或招聘站点采集。

### 阶段 E：学习检索、引用和资料研究

目标：为学习资料推荐和岗位研究提供可追溯、可更新的证据。

重点：

- 文档采集、切分、metadata、索引和检索；
- 关键词、向量和 reranking 的比较；
- 来源质量、发布时间、去重和失效检查；
- citation 与结论的逐条对应；
- Precision@k、Recall@k、faithfulness 和人工校准。

完成证据：不仅“能搜到”，而且能测量是否找对、是否漏掉、回答是否被证据支持。

### 阶段 F：建设岗位市场知识库

目标：从真实招聘数据中形成有来源、有时间范围和置信度的岗位需求视图。

重点：

- robots、网站条款、访问频率、版权和数据保留；
- 增量采集、去重、职位和技能标准化；
- 数据血缘、时间序列、样本偏差和删除；
- 采集失败、页面变化和反爬处理；
- 原始广告、标准化事实和统计结论的分层。

这一阶段本质上同时包含数据工程、搜索和合规问题，不只是“让 Agent 爬网页”。

### 阶段 G：岗位与公司风险评估

目标：输出证据、风险等级、不确定性和建议核实动作，而不是武断地给公司贴标签。

重点：

- 多源交叉验证和来源时效；
- 欺诈信号与普通招聘异常的区分；
- 误报、漏报、诽谤和申诉更正；
- 置信度校准与“信息不足”；
- 高风险结论的人工复核。

完成证据：评估可以追溯，未知信息不会被模型补全，对抗样例和反例都经过测试。

## 5. 推荐的动手练习

按照顺序完成，每次只改变一个变量：

1. 写一个最小模型调用，记录请求、响应、耗时和错误，但不记录私密正文；
2. 为输出添加 Zod Schema，分别制造缺字段、错类型、多余包装层和无效枚举；
3. 触发一次 Repair，比较“传输重试”和“语义 Repair”的不同；
4. 写一个 fake `LlmClient`，让同一失败可以在单元测试中稳定复现；
5. 修改一个 Prompt，并在同一数据集上比较修改前后的结果，而不是凭感觉判断；
6. 画出 `queued → running → needs_input → running → completed` 状态机；
7. 在本地实现最小 checkpoint，模拟进程退出后恢复；
8. 添加一个只读工具，限制参数、超时和调用次数，并测试未知工具和错误参数；
9. 建立匿名 Eval fixture，包含正常、边界和对抗案例；
10. 用相同数据和评分标准比较两个 Prompt 或模型，并让人工复核一部分结果。

对当前仓库，最适合作为第一组练习的是：

```bash
pnpm agent test src/llm/structured-output.test.ts
pnpm agent test src/workflow/agent.test.ts
```

先读测试，再故意让一个契约失败，预测错误发生在哪一层，最后恢复代码并确认测试重新通过。不要在含有真实个人资料的 fixture 中做实验。

## 6. 学习和开发应使用同一个闭环

每个功能都按下面顺序推进：

```text
问题 → 证据 → 设计 → 契约 → fake 测试 → 真实模型 Eval
    → 运行手册 → 复盘 → 把新失败加入数据集
```

### 6.1 一次小迭代应该留下什么

- 一份 Feature Brief；
- 一条证据台账记录；
- 一个明确的输入输出契约；
- 一组正常、边界、对抗和恢复案例；
- 一份实现与测试证据；
- 一条已匿名化的失败记录；
- 对文档和剩余缺口的更新。

### 6.2 建立匿名失败日记

失败通常比成功更适合学习。每条记录使用以下结构：

```text
日期 / 功能 ID：
匿名输入特征：
预期行为：
实际行为：
失败发生在哪一层：模型 / Schema / 领域规则 / 状态 / 工具 / UI
根因证据：
临时修复：
长期防线：
新增的测试或 Eval case：
仍未验证的假设：
```

不得记录真实姓名、联系方式、完整简历、API Key、原始私密 completion 或招聘账户数据。

### 6.3 使用 teach-back 检查是否真正理解

每完成一个主题，尝试不用术语回答：

1. 它解决了什么具体失败？
2. 不使用它会怎样？
3. 哪一部分必须由普通代码完成？
4. 哪些输入会让它失效？
5. 我如何用测试证明，而不是只展示一次成功？
6. 如果替换模型或框架，哪些部分应该保持不变？

答不清的问题就是下一次小实验，而不是继续堆更多抽象概念。

## 7. Agent 功能文档模板

以后每个功能都可以复制以下模板：

```markdown
# 功能名称和稳定 ID

## 用户问题与成功结果
谁遇到什么问题？什么可观察结果代表改善？

## 范围与非目标
本次做什么，明确不做什么？

## 为什么需要 LLM 或 Agent
哪些判断具有语义不确定性？普通代码为什么不够？

## 确定性边界
哪些 Schema、事实、状态、权限、预算和副作用由代码控制？

## 输入、输出和数据来源
来源、格式、所有权、时效、校验和隐私级别是什么？

## 状态与恢复
状态转换、checkpoint、重试、取消、超时和幂等性如何工作？

## 工具与权限
有哪些工具？读写范围、审批、频率和费用上限是什么？

## 失败模式
至少列出正常失败、边界输入、对抗输入、外部依赖失败和恢复失败。

## Eval 与指标
数据集、评分标准、人工校准、基线和回归门槛是什么？

## 测试证据
单元、集成、真实模型 Eval 和人工验收分别证明什么？

## 决策记录
比较过什么？采用、改造或拒绝的原因是什么？

## 剩余缺口
哪些假设仍未证明？下一道门禁是什么？
```

## 8. 如何正确理解测试

Agent 系统至少需要四层验证：

| 层级 | 适合证明 | 不能单独证明 |
| --- | --- | --- |
| 确定性单元测试 | Schema、状态转换、权限、匹配、渲染和错误分类 | 真实模型在开放输入上的质量 |
| fake LLM 集成测试 | 工作流分支、Repair、工具和恢复机制 | 真实供应商的波动、延迟和输出分布 |
| 真实模型 Eval | 事实保真、任务完成率、指令遵循、工具选择和稳定性 | 所有真实用户都会满意 |
| 人工评测与运行反馈 | 任务是否真正有用、自动评分是否可信 | 能替代持续自动回归 |

Eval 数据应包含典型、边界和对抗案例。优先使用任务特定指标，例如：

- JD 字段提取准确率；
- 不可变事实保持率和无证据陈述率；
- requirement coverage 与错误匹配率；
- Schema 首次成功率和 Repair 成功率；
- HITL 问题必要性、可回答性和恢复成功率；
- 工具选择准确率、参数正确率和越权率；
- 延迟、token、费用和失败率。

LLM-as-judge 可以辅助比较，但必须使用具体 rubric，并定期与人工标注校准。代码测试全绿只说明已覆盖行为没有回归，不代表产品决策正确，也不代表当前能力已经 operational。

## 9. 框架选型实验，而不是框架信仰

到阶段 B 或 C 时，先准备同一组验收场景：

1. 运行在任意阶段暂停并在进程重启后恢复；
2. 用户回答一个结构化问题后只重跑必要步骤；
3. 重复请求不会重复执行有副作用的工具；
4. 工具调用受权限、预算、超时和次数限制；
5. 每次状态变化和模型调用都有安全 Trace；
6. fake 模型、fake 工具和真实模型可以使用同一领域契约；
7. 替换框架不会迫使职业档案和证据模型整体迁移。

然后比较：

- 自建显式状态机；
- LangGraph 一类强调持久化和 HITL 的图运行时；
- OpenAI Agents SDK 一类提供 Agent loop、工具、session 和 handoff 的 SDK；
- 其他候选方案。

先做很小的 spike，不迁移完整业务。只有候选方案明显降低复杂度，并通过上述验收，才进入正式架构决策记录。多 Agent 也不是默认答案；只有任务确实需要不同上下文、权限或并行生命周期时才引入。

## 11. 常见反模式

- 因为有多个 Prompt，就把系统称为完整 Agent；
- 用一个巨大 Prompt 同时做提取、判断、改写、验证和渲染；
- 让 ReAct 或工具循环无限运行；
- 先选框架，再寻找它能解决的问题；
- 把 Memory 简化为聊天记录或向量数据库；
- 把可解析 JSON 当作正确领域对象；
- 让模型自己决定权限、预算和高风险副作用；
- 将真实简历、联系方式或原始 completion 写入日志和 Eval fixture；
- 只展示一次成功调用，不保留失败和回归案例；
- 只用 LLM judge，不做人类校准；
- 把代码存在、测试通过或文档写完等同于产品功能完成；
- 过早拆成微服务或多 Agent，让学习重点被基础设施淹没。
