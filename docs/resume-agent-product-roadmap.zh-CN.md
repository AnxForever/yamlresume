# Career Agent 产品路线图

> 当前代码从 YAMLResume 和简历定制能力起步，但产品本体是面向求职与职业成长全过程的 Career Agent。本文记录长期产品方向，不代表当前迭代必须一次完成。每个能力都必须单独经过：问题定义 → 调研 → 方案 → 验收标准 → 实现 → 单元/集成/Eval → 文档更新，测试通过后才能进入下一阶段。

如果你正在通过本项目学习 Agent 开发，请先阅读 [`career-agent-learning-guide.zh-CN.md`](./career-agent-learning-guide.zh-CN.md)。它解释工作流与 Agent、Runtime、Capability、Tool、State、Checkpoint、HITL、Eval 等概念，并把它们映射到当前代码和后续练习。

## 1. 产品愿景

Career Agent 不是一个“根据 JD 改几句话”的工具，而是一套围绕求职全过程工作的个人职业 Agent：

1. 理解用户真实、可证明的经历；
2. 理解实时岗位市场，而不是只依赖模型记忆；
3. 针对某个 JD 生成可信、可追溯的简历和求职材料；
4. 识别用户与目标岗位之间的能力差距；
5. 制定可执行、可验证、会随进度调整的学习计划；
6. 持续搜集学习资料并辅助完成项目、练习和复盘；
7. 分析岗位、招聘信息和公司风险，帮助用户避免虚假或不健康岗位；
8. 最终形成用户自己的“职业档案 + 岗位知识库 + 成长记录”。

### 1.1 产品层级

必须始终区分三个层级：

1. **Career Agent 产品**：面向用户的长期入口，理解意图、维护会话与运行状态、规划任务、选择能力、请求用户输入并协调结果；
2. **能力模块**：简历定制、求职材料、差距分析、学习计划、资料研究、岗位情报、岗位与公司评估等可独立验收的领域能力；
3. **工具适配器**：模型、搜索、浏览器、招聘采集、文件解析、检索、数据库和导出器等外部能力。

当前 `ResumeTailoringAgent` 属于第二层，只是第一个实现的能力模块，不能演变成整个产品的总入口。未来新增能力也不应继续堆入同一个简历工作流。

## 2. 当前阶段的唯一主目标

当前只打磨 Career Agent 的第一个能力模块：**JD 定制简历后端**。完成标准不是“模型返回了文字”，而是：

- 支持多种输入文件和图片；
- 能把输入归一化为可确认的候选人档案；
- JD 分析、证据匹配、简历生成分阶段执行；
- 不允许无来源地编造事实；
- Agent 可以主动提出结构化问题；
- 支持多种模板、样式和导出格式；
- 有真实模型验证和可重复的 Agent Eval；
- 有完整架构、权衡、测试和运行文档。

在这组能力通过验收之前，不开发岗位爬取、学习规划、公司风控等后续功能。

### 2.1 当前阶段退出门槛

P0 已经具备可运行的后端骨架，但尚未达到“完成”状态。只有以下工作都有可复现证据后，才进入后续产品阶段：

1. 十格式、多样式渲染完成开发级系统测试；继续以独立安全切片补齐 ODT、RTF、旧 DOC 等
   常见输入，并补做浏览器下载、样式保真和跨阅读器矩阵；
2. 用匿名真实案例建立 Eval Harness，记录事实保真、需求覆盖、Schema 成功率、延迟、token 和费用；
3. Human-in-the-loop 可以暂停、持久化、接收回答并从正确阶段恢复；
4. 异步 Run API、版本存储、取消/失败恢复和聚合观测完成验收；
5. 面向真实用户部署前补齐鉴权、限流、加密存储、删除策略和 PDF 编译隔离。

这是一组阶段门禁，不要求在一个晚上完成。每次只推进一个可独立验收的 vertical slice；该单元的设计、测试和文档通过后，再开始下一个单元。

## 3. Agent 交互愿景

交互方式参考 Codex、Claude Code 等 Agent 产品的核心思想，但不复制具体 UI：Agent 在不确定、缺失信息、存在风险或需要用户做产品选择时，应暂停并主动请求输入。

### 3.1 交互控件

后端应返回结构化控件，而不是只返回一段自然语言：

- `single_choice`：单选，提供 2–5 个候选项和“自定义”；
- `multi_choice`：多选技术栈、经历、目标岗位等，首期同样限制 2–5 个建议项；
- `text`：姓名、职位、短答案；
- `textarea`：项目补充、经历说明；
- `number`：人数、金额、性能提升等可量化结果；
- `date` / `date_range`：首期只处理日精度 ISO 日期；年份/月度精度需要后续
  独立设计，不能为适配控件而捏造日期；
- `url`：作品集、GitHub、项目地址；
- `file`：协议可表达既有文件引用；二进制上传与回答后重新归一化仍未实现；
- `confirm`：确认模型提取出的事实或高风险操作。

每个交互请求至少应包含稳定字段 ID、提问原因、是否必填、校验规则和隐私提示。需要用户做判断时，优先一次只问一个最重要的问题，提供少量有解释的推荐选项并允许自定义输入；需要填写事实时，则直接返回与字段类型匹配的单个输入控件。只有多个字段互相依赖、拆开会明显增加认知负担时，才组合成短表单。

### 3.2 什么时候必须提问

- 用户资料缺少姓名等构建简历的必要字段；
- 同一事实在不同文件中冲突；
- 模型无法确认一个数字、日期、公司或项目名称；
- JD 要求一个关键能力，但资料只有模糊间接证据；
- 用户要求生成一页简历，但内容无法合理压缩；
- 用户选择需要额外运行时间的 PDF、多模板批量输出；
- 将来涉及爬取、发送申请、公开发布或读取敏感账户时。

### 3.3 什么时候不应提问

- 后端可以从确定性 Schema 或已有资料中得到答案；
- 问题只影响措辞而不影响事实；
- 已经有合理默认值，且修改可逆；
- Agent 只是为了展示“智能”而制造不必要的确认。

### 3.4 运行状态机

```text
queued
  ↓
ingesting_inputs
  ↓
normalizing_candidate ──→ needs_input ──→ normalizing_candidate
  ↓
analyzing_jd
  ↓
matching_evidence ──────→ needs_input ──→ matching_evidence
  ↓
drafting
  ↓
validating ─────────────→ needs_input ──→ drafting
  ↓
rendering
  ↓
evaluating
  ↓
completed / failed / cancelled
```

`needs_input` 必须持久化运行上下文。用户回答后，从必要阶段恢复，不能无意义地从头重复所有模型调用。

## 4. 长期能力地图

### P0：可信的 JD 定制简历

- 多文件、图片、PDF、DOCX、Markdown、HTML、TXT、JSON、YAML 输入；按独立安全切片
  增加 ODT、RTF 和旧版 DOC；
- 候选人档案归一化和人工确认；
- JD 结构化分析；
- 证据 Grounding；
- 简历生成、Diff、质量报告；
- 多模板和十种格式导出；YAML、JSON、Markdown、HTML、LaTeX、PDF、DOCX、TXT、RTF、ODT
  均已开发级实现，样式保真、生产下载与更广跨阅读器兼容仍需独立验证；
- Human-in-the-loop；
- Eval、可观测性和费用统计。

### P1：求职材料扩展

- 针对 JD 的求职信；
- 自我介绍和招聘软件开场白；
- 面试问题预测；
- STAR 行为面试答案草稿；
- 项目讲解版本；
- 中英文版本一致性检查。

每种材料必须复用同一候选人事实库，不能让每个 Prompt 各自编造一套经历。

### P2：岗位差距分析和学习计划

输入：目标 JD、用户档案、可投入时间、截止日期、学习偏好。

输出：

- 能力矩阵；
- 已有证据与缺口；
- 按周/日拆解的学习计划；
- 每个阶段的可交付作品；
- 练习、测验和验收标准；
- 根据实际完成情况动态重排计划。

关键原则：学习计划不能只列课程，要形成“学习 → 实践 → 作品 → 验证 → 可写入简历证据”的闭环。

### P3：学习资料搜集和成长 Agent

- 从官方文档、课程、论文、开源仓库搜集资料；
- 记录资料来源、发布时间、难度、时长、适用技能；
- 避免只按热度推荐；
- 根据用户当前水平选择资料；
- 生成练习并评审结果；
- 把新完成的项目和结果写回职业档案，但必须由用户确认。

### P4：真实岗位市场知识库

- 合规地采集公开招聘信息；
- 遵守 robots、网站条款、频率限制和数据保留要求；
- 对岗位名称、技能、年限、学历、薪资、城市、行业进行标准化；
- 去重、识别重复招聘和长期挂岗；
- 建立时间序列，区分短期热词与稳定需求；
- 按岗位族生成能力图谱、技能共现、地区差异和趋势报告。

知识库不能把招聘广告直接当事实。每条结论应记录样本数、时间范围、数据来源和置信度。

### P5：岗位和公司健康度评估

可能的信号：

- JD 是否具体、职责与要求是否合理；
- 薪资范围与职责、城市和年限是否匹配；
- 是否存在收费培训、押金、设备购买等诈骗信号；
- 联系方式、域名、公司主体是否一致；
- 是否存在异常高薪、过度承诺、紧迫施压；
- 岗位是否长期重复发布；
- 公司公开登记、官网、招聘账号、新闻和员工反馈是否互相印证；
- 工作时间、试用期、社保、合同等表述是否存在风险。

输出必须是“证据 + 风险等级 + 不确定性 + 建议核实动作”，不能无依据给公司定性。涉及公司声誉时需要来源、时间和免责声明，并允许被评估方信息不完整。

## 5. 建议的长期架构边界

```text
Web / App / CLI
        │
        ▼
Career Agent Runtime
├── 意图理解与任务规划
├── Capability Registry 与路由
├── Run / Session / Checkpoint
├── Human-in-the-loop 与审批
├── 权限、预算、隐私和安全策略
└── 事件流、Trace、成本和 Eval
        │
        ├── Resume Tailoring（当前能力）
        ├── 求职材料与面试准备
        ├── 岗位差距与学习计划
        ├── 学习资料研究与辅导
        ├── 岗位市场情报
        └── 岗位与公司健康度评估
        │
        ▼
共享领域模块
├── 职业档案、事实、证据、来源和确认状态
├── 目标岗位、JD、能力模型和成长记录
└── 产物、引用、版本和审计记录
        │
        ▼
工具适配器
├── LLM、搜索、浏览器、招聘采集和 MCP
├── 文件解析、OCR、检索和知识库
└── 数据库、对象存储、通知和文档导出
```

顶层 Agent 应能根据用户目标选择和组合能力，但每个高风险领域能力仍应使用有界、可验证的工作流。模型可以提出计划和工具调用，确定性代码负责 Schema、权限、预算、事实约束、状态转换和副作用审批。这样既不会把整个产品限制成一条固定流水线，也不会把所有控制权交给无限循环的模型。

早期仍建议使用模块化单体，并让能力模块通过窄接口接入 Capability Registry。模型、搜索、存储和采集等外部依赖通过可替换适配器接入；只有当采集任务、模型任务或文档处理出现独立扩缩容和部署需求时，才拆成服务，避免为了“像大项目”而提前引入微服务复杂度。

Agent 框架不是产品架构本身。应先稳定 Career Agent 的运行、交互、能力和工具接口，再用同一组验收场景比较自建状态机与候选框架。框架必须能够被替换，不能让职业档案、证据模型和领域能力依赖某个厂商的 Agent 对象。

## 6. 每个未来功能的强制开发门禁

1. 写 Feature Brief：用户问题、输入、输出、范围、非目标；
2. 调研官方资料、成熟产品和开源实现；
3. 记录采用、改造或拒绝哪些方案以及原因；
4. 定义失败模式、隐私和安全边界；
5. 写验收标准和 Eval 数据集；
6. 做最小 vertical slice；
7. 每个单元完成后跑单元测试；
8. 功能完成后跑集成测试、真实模型 Eval 和回归；
9. 更新架构、接口、运行和学习文档；
10. 测试通过后才能进入下一个功能。

## 7. 明确不做的错误方向

- 一个巨大 Prompt 完成所有任务；
- 用“Agent”名义引入无边界循环；
- 把用户隐私、API Key 或简历全文写进日志；
- 没有时间和来源的岗位知识库；
- 只用 LLM 打分、没有确定性断言的 Eval；
- 为了追求模板数量牺牲 ATS 可读性和内容真实性；
- 在后端协议未稳定前投入大量自定义前端。
